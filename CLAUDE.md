# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Deterministic, data-driven Pokémon hero shooter: TypeScript, esbuild, `node:test` via tsx. One Pokémon per player; the shipped modes are the training range and Hold (`src/mods/index.ts`), with co-op waves (T1) and 3v3 hero bots (T2) after the overhaul (decision D6). The 3D overhaul (three.js, a mesh world, Rapier) is under way: plan, decisions and task order in docs/OVERHAUL_3D.md; until its cutover task X1a, new systems land behind flags that default off. The cutover is the 3D training range (decision D9): X1a makes the 3D stack the game once the 3D range plays, and Hold leaves `MODES` there until G2b. The old tile game is frozen (decision D8): with every flag off it is test ground until X1b deletes it, no longer a product requirement, though merges still deploy it until the cutover. The build is a static site deployed to GitHub Pages (`.github/workflows/deploy.yml`): `dist/index.html` holds the code (≤ 3 MB, the build fails above it), and the Pokémon art (`dist/art/`) and music (`dist/music/`) are fetched files, so serve the folder; browser tools open `file://` with `--allow-file-access-from-files` (`tools/README.md`). The README has the full picture. This file lists only what a session needs up front. The work queue and its status are in `docs/ROADMAP.md`. The pivot from the survivor game is recorded in `docs/hero-shooter-pivot.md` (a closed record: decisions §10, progress §11; its open items moved to the roadmap); the survivor game is on the `survivor-final` tag.

## Working with the owner
- One task per chat, on its own branch off `main`.
- Never push `main` without the owner's go: pushing `main` deploys the live site.
- `npm run check` must pass with zero reds before work is called done.
- Engineering choices (decision D10, docs/ROADMAP.md "Owner decisions"): make one yourself when all three hold: it can be undone without moving a recorded decision, a contract other systems read, or a shipped baseline; a test or gate covers it; it has a measurable acceptance criterion. Record each such choice where the task's records go (alternatives, numbers, why).
- Stop and ask for: a design, feel, look or scope question that isn't recorded (in `docs/` or `docs/ROADMAP.md`), or anything a player experiences as a rule; anything costly to undo (a contract, a version bump that regenerates baselines, the renderer or shading language, removing something no task names); an unexplained replay or `gameplayHash` move (a flag-off hash moved by a change the task names is re-recorded once, with the reason in the commit: D8); a test that looks wrong. Tests are the spec: never edit one to make it pass. One exception (D8): a test whose only subject is "flag-on equals tile" may be retired by the task that improves on it, named in the report, with the reason in the commit.
- At the end of each task, update `docs/ROADMAP.md` (status, and any follow-up found).
- Report as: commits, gates (each command and its result), deviations from the brief, "Decided without asking" (the D10 choices), found-not-fixed, then the stop or the next step.
- When the owner must do something (merge, push, view a page or capture, run a browser check, answer a question), put the steps under a heading `## For you to do`. Write them in the instructional style below. Give exact commands in code blocks, one command per block, with no inline `#` comments (zsh). When the owner must look at a file (an image, a capture, a page, a log), give its full absolute path and a command that opens it, for example `open /Users/.../shot.png`. If a page loads `art/` or `music/` and cannot open from `file://`, give the command that serves it instead (`tools/README.md`).

## Instructional writing style

Apply this style only when you write or edit instructional text: tutorials, procedures, prompts, requirements and specifications for humans or AI systems. Write all other responses normally.

Use a plain technical style inspired by ASD-STE100 Simplified Technical English:
- Write short, direct sentences. Give one instruction per sentence.
- Use active voice and concrete, unambiguous words.
- Use the same term for the same concept throughout.
- Write naturally. Use formal language only when the task requires it.

State all necessary requirements clearly and precisely. Do not add constraints that are not necessary. Include context, reasons or examples only when they help the reader do the task correctly. Remove unnecessary words, but keep all technical detail, exact constraints and important nuance.

## Commands (repo root)
- One suite: `npx tsx --test tests/<name>.test.ts` (add `--test-name-pattern "<regex>"` to pick a single test)
- All tests: `npm test` (headless, no browser)
- Types: `npm run typecheck` (CI runs it too)
- Before calling work done: `npm run check` (typecheck, tests, production build; writes `dist/`). It must pass with no red: the deploy workflow runs `npm test` before its build, so any red test blocks the GitHub Pages deploy.
- Replay baseline: `npx tsx scripts/checksum.ts [scenario|all] [--update]`. It runs the sixteen scenarios of `tests/fixtures/scenarios.ts` (scripted input tracks on the range, Mt. Moon, Shoal Grotto, Cinder Crater, a Shrine Gorge Hold, the swap range, the range Charmander and the Hold again on Rapier, ids ending `-rapier`, the Hold on the navmesh, `-navmesh`, the range Mewtwo with `rules.aim.viewSight`, `-viewsight`, and the range Charmander and the Hold on the 3D stack, both flags on, `-3d`) and compares their 10 s checkpoints and end hash with `tests/fixtures/replays.json` (`tests/replays.test.ts` asserts the same in `npm test`, plus each scenario's coverage counters). A sim change that is not meant to change behaviour must print every scenario "as recorded"; a hash that moves is a stop, not something to re-record. `--update` rewrites only the scenarios it ran, and the commit that changes the fixture says why. A new feature may land flagged off with a scenario that must print the baseline; retire the flag and its off path once it defaults on and is accepted (docs/hero-shooter-pivot.md §7).
- Performance-sensitive sim changes: `npx tsx scripts/perf-sim.ts 500 --repeat 3 --gate` (the crowd of `scripts/lib/crowd.ts`; baseline p95 0.689 ms, p99 0.936 ms; `--aim` adds the crosshair ray; `--physics rapier` runs on the physics flag and prints physics' share). Since decision D8 the flag-off run is required only for tile-only code, until X1b; a flag-on run is the gate of the task that changes that path.
- Physics (`src/physics/`, docs/OVERHAUL_3D.md "Physics (I1a)"): Rapier loads asynchronously once per process; a test that builds a run with `rules.physics.engine = 'rapier'` imports `tests/setup/physics.ts`, and a run on it is freed with `disposeRun(ctx)` (wasm memory never shrinks). Node ≥ 22.15.
- Movement, collision or navigation changes: `npx tsx scripts/navwalk.ts all 5` (real walkers of every size class reach every mandatory space, 0 failures; docs/SIZING.md) and `npx tsx scripts/stuckwatch.ts all 3` (live deadlock watch; current output: 14 player episodes, 3 TRAPPED at River Gorge seed 3, 31 enemy episodes, all logged in pivot §11 and open in docs/ROADMAP.md F1; compare before and after, a new TRAPPED is a failure). Since decision D8 these flag-off runs are required only for a task that touches tile-only code, until X1b deletes it. With both flags on (`--physics rapier --nav navmesh`) the stuckwatch gate is no TRAPPED except at a listed site (`--known tests/fixtures/stuckwatch-known.json`: River Gorge seed 3's pit, owner 2026-11-27; `--compare` against the flag-off run stays as a diagnostic) and navwalk passes on its known list (`--known tests/fixtures/navwalk-known.json`, docs/ROADMAP.md F74).
- Dev server: `npm run dev` (http://localhost:5173)

## Architecture rules (details in README §Architecture)
- Layering, enforced by `tests/imports.test.ts` (README §Architecture rule 1): `src/world/` never imports `src/sim/`, `render/`, `ui/`, `audio/`, `input/` or `assets/`, and `src/sim/` never imports `render/`, `ui/`, `audio/`, `input/` or `assets/`; both must run in Node. For the 3D overhaul, only `src/physics/` imports Rapier (`@dimforge/*`), only `src/nav/` imports recast (`recast-navigation`, `@recast-navigation/*`), and `src/sim/`, `src/world/`, `src/physics/`, `src/nav/` and `src/core/` never import `three`.
- Fixed 1/60 s ticks, one RNG stream per system (spawn, combat, world, ai). No `Math.random`, and no clock in sim or worldgen output (`performance.now()` is used for timing metrics only).
- Tunable numbers live in `src/rules/` (`defaults.ts` and friends). Systems read `ctx.rules`, never literals. Kept switches are real tunables (`hazards.enabled`, `aim.foliageCover`, `aim.deviceAssist`, the `caps` sub-flags); do not add an off path for an accepted feature.
- The sim emits events. Render, audio and UI only react to them.
- Modes and mods (`src/mods/`): a `Mode` is rule overrides plus `Mod`s; a mod adds, removes or replaces systems. `MODES` (reachable by `?go=1&mode=`) is `[RANGE, HOLD]`; the title offers `TITLE_MODES`, `[RANGE]` (Hold is URL-only until T2: `?go=1&mode=hold&map=<habitat>`); `RANGE_SWAP` is the opt-in swap system's own mode. `RANGE` (with `solo`) is also the plain foundation tests and gates run on.
- Heroes: stats on the level-50 canon curve (`src/rules/stats.ts`), kits from `openingMove` / `heroKit` with authored `HERO_KITS`, the hero pick from `PROTOTYPE` / `FEATURED` (`src/rules/heroes.ts`, docs/HEROES.md). A `KIT_TUNING` test refuses a new unlogged power-0 damaging move in a kit.
- Each subsystem has a doc in `docs/` (HEROES, RANGE, SQUAD, SYSTEMIC, SPAWNING, SIZING, LOCOMOTION, CONTROLS, HAZARDS, HABITATS, LOCATIONS, THIRD_PERSON, CAMERA, AUDIO, …). Read the matching doc before changing a subsystem, and update it when its rules or numbers change. `docs/CUSTOMISING.md` is the how-to for roster, size, map and target changes.
- Enemies come from target sets (`src/rules/targets.ts`, `src/sim/targets.ts`), the Hold's `RAID_PARTY` (`src/sim/modes/hold.ts`) and, in tests and gates only, `scripts/lib/crowd.ts` (not a game system; no replay scenario uses it). There are no spawn pools, no director and no elite, alpha or boss roles. The role bits are `raider` and `target` (set by the spawner) and `ranged`, `healer`, `swarm`, `flying` (set by `spawnEnemy` from the species). Per-species facts (preferences, restrictions, size pins) live in `src/rules/profiles.ts`, placement in `src/sim/placement.ts`. Sizes come from `rules.size` through `bodyOf` / `enemyRadius` / `partnerRadius` / `footprintOf` / `partnerFootprint` (`src/rules/sizing.ts`); never derive a body radius in the sim. Walls stop footprints through `World.moveBody` only, and wide footprints route on `src/world/navblocks.ts`, which the location `wide` gate also reads.

## Habitat maps (`src/world/habitat/`, `docs/HABITATS.md`)
- Frozen (decision D8, 2026-11-25): no work on the habitat or location generators and no `HAB_VERSION` or `LOC_VERSION` change; a task touches this code only to delete it (X1b). The bullets below describe the frozen tile game. The "layout would move" stop went with the freeze; an unexpected `gameplayHash` move of a generated 3D map is still a stop (docs/WORLDGEN3D.md Q19).
- A layout is fully determined by recipe + variant + seed + `HAB_VERSION` (`src/world/habitat/index.ts`). A generator change that alters any accepted layout needs a `HAB_VERSION` bump. Compare timing and retry behaviour against `docs/habaudit/baseline.json`. The navigation profiles (`profilesFor`, `src/world/habitat/mode.ts`) are frozen constants, and they stay so: the `HAB_VERSION` bump once planned for making a hero of one of the 54 ready species that exceed them will not happen, since roadmap item 6 is dropped (D7) and the generator is frozen (D8).
- Gates to run after touching habitat, hazard or objective code (tile-only code: required only for a task that touches it, until X1b; D8): `npx tsx scripts/habstate.ts`, `scripts/habplay.ts all 6 1 --raid` (the shorter `all --raid` runs 0 cases and exits 0), `scripts/hazplay.ts`, `scripts/habaudit.ts` (slow; it rewrites `docs/habaudit/baseline.json`, so diff it and restore it unless the change is meant to move it). `tests/habitat*.test.ts`, `habstate`, `habaudit`, `habtac` and `hazards` assert the same checks.
- Hold Raid party: it spawns at team B's staging, 33–47 m from the point. `rules.enemy.despawnDistance` (46) relocates any enemy that is not pinned farther than that from the player to a ring ahead of them, which would skip the approaches. `src/sim/enemies.ts` pins the Raiders of an active habitat Hold and every training target. Check the same relocation before adding any other far-spawned actor on these maps.
- Tactical playtest evidence (survivor build, with a hero-core status note), seeds worth replaying and the human checklist: `docs/HABITAT_PLAYTEST.md`. The current Hold read is the fighting probe in pivot §11.

## Generated and oversized files
- Generated by `scripts/build-content.mjs`; do not hand-edit: `src/content/pokedex.ts`, `src/content/art.json`, `src/content/icons.json`, `src/content/catalogue.ts`, `content/report.json`.
- `src/content/catalogue.ts` (130 KB) is the reference catalogue, not game species: regenerate it alone with `node scripts/build-content.mjs --catalogue-only` (add `--catalogue-out <dir>` for an isolated copy). Authored input is `content/catalogue.json`; read it through `src/rules/catalogue.ts`. Nothing in `src/sim/`, `src/world/`, `src/render/`, `src/ui/` or `src/rules/species.ts` may import it — a catalogue record inside `SPECIES` takes a registry index and moves every replay hash. `tests/catalogue.test.ts` is the gate.
- Never read these whole. Use grep or targeted ranges: `src/content/art.json` (12.1 MB), `src/content/icons.json` (470 KB), `content/report.json` (1.6 MB), `docs/Pokemon_*_Specification.md` (90–230 KB). The `docs/*.xlsx` and `content/preview/*.png` files are binary.

## Browser checks
- `tools/*.mjs` and `tests/browser/*.py` drive headless Chromium. Playwright is not a dependency: run `npm i --no-save playwright` first; the Python checks run from a `.venv` made from `tests/browser/requirements.txt` (setup in `tools/README.md` "Python checks"). Usage is in `tools/README.md`. `tests/browser/range.py` is the merge check (title, hero pick, fire at a dummy, a Breakthrough), run by hand, not in `npm run check`; `--query physics=rapier` runs it on the physics flag.
- Capture mode (`?capture=1`): the sim only steps through `pokewatch.advance(seconds, {frames})`, which runs `round(seconds/frames/dt)` steps per frame. Pass `frames = seconds × 60` (one step per frame). Anything else silently under-steps (`advance(1.4, {frames: 70})` runs 1.17 s) and particles never appear.

## Parallel sessions
- Several Claude sessions often work in this checkout at once. Check `git status` before editing, and leave alone uncommitted changes you didn't make.
- `npm run build`, `npm run dev` and `npm run check` all write `dist/`. For screenshot captures, build into a private directory instead: `node scripts/build.mjs --out <scratchpad dir>`, then pass its `index.html` to `tools/cap.mjs` (the page needs the `art/` and `music/` written beside it). This keeps you from overwriting another session's build.

## Agent skills
- `/grilling` before committing to a change with undecided design questions whose wrong answer is expensive to undo — e.g. a `WORLD_VERSION` or `MODEL_VERSION` bump, a regenerated baseline, moved replay hashes, or a contract other systems read (hazards × objectives × enemies). Not for mechanical work — the decisions are already made and only transcription is left.
- `diagnosing-bugs` for a bug or regression with no deterministic repro yet (wrong sim behaviour at a known seed, a hash that moved unexpectedly, a layout failing a gate, a `perf-sim --gate` regression). Not for a failing test that already names its cause.
- Both are vendored in `.claude/skills/`; see `.claude/skills/README.md` for provenance and local edits. Review stays the built-in `/code-review`.
